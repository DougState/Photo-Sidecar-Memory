# HTML-First Output Policy

> Rationale: [Thariq Shihipar — HTML's Unreasonable Effectiveness with Claude Code](https://baoyu.io/translations/2026-05-08/trq212-status-2052809885763747935).
> Markdown is fine for chat. For anything you'd share, save, or re-read — produce HTML.

---

## 1. Output Format Policy

When you need to emit a substantial artifact, choose the format **before** you start writing:

**Use HTML when the artifact is any of these:**
- A spec, implementation plan, or exploration of design alternatives
- A code review, PR explainer, or "how does X work" walkthrough
- A research report, weekly summary, or incident write-up
- A design mock, prototype, or component preview
- A custom editing UI (re-prioritize, tag, tune params, edit config)
- Anything likely to be shared with another human, or re-opened later
- Anything that would be longer than ~50 lines as Markdown

**Use Markdown when:**
- The reply fits in chat (under ~30 lines, no tables, no diagrams)
- You're editing a repo's existing `README.md`, `ARCHITECTURE.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, or anything inside an established Markdown docs convention
- You're writing a commit message, PR body, or GitHub issue
- The user explicitly asks for Markdown

**When unsure: ask once.** ("HTML artifact or Markdown reply?") Then remember the answer for the rest of the session.

## 2. HTML Artifact Conventions

Every HTML artifact you produce must follow these rules:

- **Location:** `~/claude-artifacts/<YYYY-MM-DD>/<kebab-slug>.html`. Create the dated directory if missing.
- **Self-contained:** one file. Inline `<style>` and `<script>`. No build step, no `npm install`, no local imports.
- **Allowed CDNs (only):** `https://cdn.tailwindcss.com` (Tailwind Play CDN) and `https://cdn.jsdelivr.net/npm/lucide@latest` for icons. Nothing else — the file must open offline-ish.
- **Mobile-responsive:** include `<meta name="viewport" content="width=device-width, initial-scale=1">`. Use flex/grid, no fixed pixel widths on layout containers.
- **Self-documenting footer:** end every artifact with a small footer:
  ```html
  <footer class="text-xs opacity-60 mt-12 pt-4 border-t">
    <details>
      <summary>Generated by Claude · <time>{ISO timestamp}</time></summary>
      <pre class="mt-2 whitespace-pre-wrap">{the prompt that produced this artifact}</pre>
    </details>
  </footer>
  ```
- **No external images.** Use inline SVG or `data:` URIs so the file stays portable.
- **Title tag matches H1.** Set `<title>` so browser tabs are scannable.

## 3. Required Capabilities Per Artifact Type

Before emitting, confirm the artifact has the listed elements for its type.

### Specs and Plans
- Tabbed sections: **Overview · Data Flow · Edge Cases · Test Plan · Open Questions**
- At least one inline SVG diagram showing data flow or component relationships
- Code snippets with syntax highlighting (use a tiny inline highlighter or just `<pre><code>` with a monospace style — never paste rendered terminal colors)
- Mermaid-style flowcharts rendered as native SVG, not Mermaid script tags
- A "decisions made / decisions deferred" summary near the top

### Code Review and PR Explainers
- Side-by-side diff view (two columns, line-aligned) — not unified diff
- Inline annotation bubbles with severity color-coding: blue (info), amber (consider), red (blocking)
- Per-file table of contents at the top with anchor links
- "Jump to next concern" buttons that scroll to the next non-info annotation
- Each concern includes: file:line, severity, what, why, suggested fix

### Reports and Research
- Executive summary in the first viewport (no scrolling required to get the gist)
- SVG charts for any quantitative data — **never** ASCII art, **never** Unicode block characters as bars
- Expandable detail sections (`<details>`) so the page is short by default
- Sources/citations list at the end with clickable links
- "Last updated" timestamp visible

### Design Prototypes
- Live preview area (the design itself, rendered)
- Sliders, color pickers, and number inputs for every tunable parameter
- Live two-way binding: changes update the preview instantly
- A "**Copy as prompt**" button that serializes current state into a paste-ready prompt block
- Reset-to-defaults button

### Custom Editing UIs
- Drag-and-drop or form-based editor matched to the data shape
- Inline validation with helpful error messages (don't just turn fields red)
- **Always** an export button — pick the right one: `Copy as JSON`, `Copy as Markdown`, `Copy as prompt`, or `Download .csv`
- Preserve unsaved-changes state with `beforeunload` warning

## 4. Interactivity Primitives

Reach for these patterns by default. Implement them in vanilla JS — no React, no Vue, no build tools.

**Tunable input + live readout:**
```html
<label class="flex items-center gap-3">
  <span class="w-32">Padding</span>
  <input type="range" min="0" max="64" value="16" oninput="this.nextElementSibling.value=this.value+'px'">
  <output class="font-mono w-16">16px</output>
</label>
```

**Copy-to-clipboard button:**
```html
<button onclick="navigator.clipboard.writeText(document.getElementById('payload').textContent).then(()=>this.textContent='Copied')">
  Copy
</button>
```

**Progressive disclosure** — prefer `<details><summary>` over scrolling walls of text.

**Tabs** — one consistent vanilla implementation per artifact:
```html
<div class="tabs" data-tabs>
  <nav>
    <button data-tab="overview" class="active">Overview</button>
    <button data-tab="dataflow">Data Flow</button>
  </nav>
  <section data-panel="overview">...</section>
  <section data-panel="dataflow" hidden>...</section>
</div>
<script>
  document.querySelectorAll('[data-tabs] nav button').forEach(b => b.onclick = () => {
    const tabs = b.closest('[data-tabs]');
    tabs.querySelectorAll('nav button').forEach(x => x.classList.toggle('active', x === b));
    tabs.querySelectorAll('[data-panel]').forEach(p => p.hidden = p.dataset.panel !== b.dataset.tab);
  });
</script>
```

## 5. Design System Reference

Before generating any HTML artifact, **read `~/claude-artifacts/_design-system.html` first** and match its tokens (colors, spacing scale, type ramp, component look).

If `_design-system.html` doesn't exist:
1. Scan the five most recent files in `~/claude-artifacts/**/*.html`.
2. Extract the recurring color palette, font stack, spacing scale, and component patterns.
3. Generate `_design-system.html` as a single page that displays each token and component.
4. If there are no prior artifacts, ask: "What aesthetic do you want? (clean/editorial, dense/technical, playful, brutalist, your-brand…)" then generate accordingly.
5. Use the new design system for the current artifact.

The design system file is the source of truth. When the user says "make it match my style," update `_design-system.html` first, then regenerate.

## 6. Anti-Patterns

Never do these — they're the failure modes the article calls out.

- **No ASCII-art diagrams.** If you'd reach for `+----+` or box-drawing characters, draw SVG instead.
- **No Unicode color hacks.** Never use `🟥🟩🟦` or block characters to fake colored squares. Use real CSS.
- **No Markdown plans over 100 lines.** If you've passed 100 lines of Markdown, stop, switch to HTML, regenerate.
- **No external build tooling.** No `package.json`, no Vite, no bundlers. The artifact opens by double-clicking the file.
- **No external images.** SVG or `data:` URIs only.
- **No raw API keys, no `.env` paste-throughs.** Even in editing UIs, mask secrets.
- **Don't ship a "framework"** — each artifact is purpose-built and disposable. Resist building a reusable component library inside the artifact.

## 7. Hand-off Rules

After generating an HTML artifact:

1. Print one line in chat: `Created <slug>.html — <one-sentence summary>`
2. Print the absolute path on the next line so it's click-to-open in the terminal.
3. Then offer (don't auto-execute) one or more of:
   - "Open it in your browser?"
   - "Want me to upload it to S3 and give you a shareable link?"
   - "Iterate on the design — what would you tune?"

Do not paste the entire HTML back into chat. The file is the deliverable.

---

## 8. Token Cost — Acknowledged Trade-off

HTML costs **2–4x more output tokens** than the equivalent Markdown. That's the deal. Don't apologize for it mid-task, don't propose Markdown as a "lighter" alternative unless the user asks. The article's framing: in a 1M-token context window, the readability and shareability win is worth the token spend by orders of magnitude.

If a user pushes back on token cost, point them at this section and ask whether they'd like to switch to Markdown for this specific task.

---

## 9. When This Policy Is Overridden

A repo's own `CLAUDE.md` (project-level) overrides this file. If you're working inside a repo whose `CLAUDE.md` says "use Markdown for plans," do that. This file is the **default** for everything outside a project-specific override.
